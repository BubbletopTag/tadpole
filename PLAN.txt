0. WHAT SURVIVED THE RETARGET  (most of it)
--------------------------------------------------------------------------------
The device changed; the approach did not. Still true:

  * ARCH B (qemu-user + device shim) is still the primary path. §2.
  * The shim design (shared mmap'd file + native SDL viewer) is unchanged. §7.
  * Flash Lite is still the GUI, so the system UI is still "an easy title".
  * strace/gdb are still available; capture ground truth on hardware. M2.
  * ALSA, tslib, evdev, UBIFS-on-UBI, mdev hotplug — all the same.
  * The power/hwmon driver still exists (hwmon-lf2000.c). §4.
  * The framebuffer ABI is LITERALLY THE SAME FILE — see §3. Big win.

What genuinely changed, and mostly for the better:

  + Cortex-A9 instead of ARM926. QEMU's ARMv7/A9 support is mature and
    well-trodden (vexpress-a9 etc.). Full-system emulation (M9) went from
    "grim" to "plausible".
  + U-Boot instead of Emerald Boot. Standard, documented, source in hand,
    normal ATAG/machine-ID handoff, and a serial console you can drop into.
  + A COMPLETE Nexell SoC HAL with per-block .c AND .h. §1. This is a real
    datasheet substitute and it covers every peripheral, not just display.
  + The display moved to the standard Linux framebuffer API. §3. Simpler.
  - Hardware AES engine + per-chip ECID. §6. The DRM risk got real.
  - ARMv7 soft-float uClibc is an unusual ABI combo; watch for surprises.

3. THE DISPLAY PATH — SIMPLER THAN LEAPPAD1
--------------------------------------------------------------------------------
*** THE /dev/mlc + /dev/layer0..2 CHARACTER-DEVICE INTERFACE IS GONE. ***

Evidence: include/linux/ in the LF2000 kernel contains only
    linux/lf1000/lf1000fb.h      <-- the framebuffer ABI, PRESERVED VERBATIM
    linux/lf1000/screen.h
    linux/lf2000/gpio.h, gpio_ioctl.h, vr5_ioctl.h, lf2000vip.h
There is NO mlc_ioctl.h and NO dpc_ioctl.h. The MLC/DPC ioctl surface that
dominated the LeapPad1 plan is not exposed to userspace on this platform.

What userspace gets instead: STANDARD LINUX FRAMEBUFFER DEVICES.
    drivers/video/lf2000fb.c      the LF2000 fb driver
    drivers/video/lf1000fb.c      kept alongside for compatibility
    drivers/video/nexell/dpc/dpc_drv.c    display controller
    drivers/video/nexell/lcd/nxp3200_lcd_vtk.c
    drivers/video/nexell/rotator/, vip/, decoder/

So the contract is /dev/fb0 (and probably /dev/fb1, /dev/fb2 for the
additional layers — [VERIFY] against your device) plus the extensions
already documented in lf1000fb.h:

    LF1000FB_IOCSALPHA / IOCGALPHA        _IOW/_IOR('m', 1/2, ...)
    LF1000FB_IOCSPOSTION / IOCGPOSTION    [sic — typo is in the header]
    LF1000FB_IOCSVIDSCALE / IOCGVIDSCALE  hardware scaling
    FBIO_WAITFORVSYNC                     _IOW('F', 0x20, __u32)
  plus layer format / priority / planar packed into fb_var_screeninfo.nonstd:
    LF1000_NONSTD_PLANAR   bit 23, mask 0x1
    LF1000_NONSTD_PRIORITY bit 24, mask 0x3
    LF1000_NONSTD_FORMAT   bit 20, mask 0x7
    NONSTD_TO_PLANAR(x) / NONSTD_TO_PFOR(x) / NONSTD_TO_POS(x)

WHY THIS IS GOOD NEWS:
  ~90% of this is the ordinary Linux fb API — FBIOGET_VSCREENINFO,
  FBIOGET_FSCREENINFO, FBIOPUT_VSCREENINFO, FBIOPAN_DISPLAY, mmap. All
  standard, all trivially shimmable, all already understood. Only four
  LeapFrog ioctls plus the nonstd bit-packing are custom, and we have the
  header that defines them. The dirty-bit commit model that would have been
  fiddly on LeapPad1 is gone.

REGISTER-LEVEL REFERENCE (for M9, and for when the fb driver is ambiguous):
  arch/arm/mach-nxp3200/prototype/module/ is Nexell's own SoC HAL, with
  BOTH .c and .h for every block:
      nx_mlc      nx_dpc      nx_vip      nx_csc      nx_rotator
      nx_deinterlace          nx_idct     nx_audio    nx_dma
      nx_intc (interrupt ctrl)            nx_timer    nx_uart
      nx_gpio     nx_i2c      nx_adc      nx_pwm      nx_rtc
      nx_sdhc     nx_sspspi   nx_ohci     nx_clkpwr   nx_alive
      nx_ecid     nx_mcus/nx_mcud (memory ctrl)       nx_mpegtsif
  This is a far more complete hardware reference than LF1000 ever had, and
  it covers EVERY peripheral — which is exactly what a QEMU machine model
  needs. nx_intc.c + nx_timer.c + nx_uart.c are the three that make M9 start.

--------------------------------------------------------------------------------
drivers/hwmon/hwmon-lf2000.c exists alongside hwmon-lf1000.c.

On LeapPad1 that driver registered a SEPARATE input device named exactly
"Power Button" (phys "lf1000/power_button"), used as a general power-event

>>> ACTION: read hwmon-lf2000.c and confirm the device name, the phys

    Expect the same design; verify the strings, because the shim has to

    KEY_EQUAL normal         KEY_UP external power
    KEY_KPEQUAL NiMH         KEY_PAGEUP NiMH charger

5. WHY THE STOCK KERNEL STILL WON'T BOOT IN PLAIN QEMU  (but it got closer)
--------------------------------------------------------------------------------
Same conclusion as before — a machine model is required — but the reasons
have shifted and the work is smaller:

  STILL FATAL:
    * No machine model for NXP3200. QEMU has no board for it, so peripheral
      MMIO (interrupt controller, timers, UART, memory controller) is
      unmapped and the kernel dies before console.
    * The early UART address is board-specific; wrong address = zero serial
      output, exactly as you saw on LeapPad1.

  NOW MUCH EASIER:
    * Cortex-A9 is a first-class QEMU CPU. No CPU work at all.
    * U-Boot 2010.06 is standard and its source is in the drop, so the
      handoff (machine ID, ATAGs, memory map) can be read rather than
      reverse-engineered — and U-Boot itself can be run under QEMU as a
      bring-up target before you attempt the kernel.
    * The full Nexell HAL (§3) supplies the register maps for exactly the
      blocks a machine model must implement.
    * arch/arm/plat-nxp3200/{bid,e2k,l2k,m2k,vtk}/include/cfg_*.h give
      per-board iomap, memory map, GPIO and NAND layout:
          cfg_iomap.h cfg_mem.h cfg_sys.h cfg_gpio.h cfg_nand_map.h
      That is a board file handed to you.

  BOARD TAGS (defconfigs): nxp3200_{l2k,m2k,bid,vtk}_defconfig plus
  _surgeon / _sd / _ubi / _nfs / _ramfs variants.
  l2k is almost certainly LeapPad2 and m2k Leapster GS [VERIFY via
  /proc/cpuinfo or dmesg on your device]. e2k and vtk are other boards
  (vtk = Nexell's own validation kit).

  START M9 FROM: nxp3200_l2k_surgeon_defconfig. Surgeon is the USB-loaded
  recovery kernel — designed to be dropped into RAM and run, so it is a much
  softer bring-up target than the NAND kernel. Its source is a separate
  package (linux-surgeon-2.6.37+svn-r1575).

6. DRM — *** LARGELY RETIRED. THE BASE FIRMWARE IS NOT ENCRYPTED. ***
--------------------------------------------------------------------------------
TESTED 2026-07-27 against the extracted stock rootfs:
    LF/Base/LPAD/main.swf        -> "Macromedia Flash data, version 8"
    LF/Base/LPAD/AboutMe.swf     -> "Macromedia Flash data, version 8"
    Brio/lib/libDisplayMPI.so    -> plain ELF 32-bit ARM EABI5 shared object
    Brio/Module/libDisplay.so    -> plain ELF 32-bit ARM EABI5 shared object
    bin/AppManager               -> plain ELF 32-bit ARM EABI5 executable
    LpadAssets_en/Data/*.json    -> plaintext JSON, readable
  Nothing under /etc or /usr/bin references an AES/crypto device, and
  `strings AppManager` shows no /dev/aes, /dev/crypto or ecid references.

CONCLUSION: the entire base system — UI, Flash content, Brio libraries,
assets — ships in the clear. The hardware AES engine and ECID exist, but the
system firmware does not appear to use them for content protection. There is
NO crypto obstacle anywhere on the path from M1 to M6. Content is SWF 8
(Flash 8 / ActionScript 2 era), which Flash Lite 3.x handles.

REMAINING UNKNOWN (honest caveat): this proves the BASE FIRMWARE is
unencrypted. It does NOT prove cartridge content is. Carts could still carry
protection, and that only shows up at M7. But the risk is now scoped to one
milestone instead of threatening the whole project.

For reference, the hardware that exists but appears unused for DRM:
    drivers/crypto/nxp3200/  nx_aes.c, nx_aes_linux.c, nx_aes_regmap.h,
                             nx_aes_ioctl.h, sysapi.c/h
    mach-nxp3200/prototype/module/nx_ecid.c/.h   per-chip unique ID
Original analysis follows, retained for the M7 cartridge question:

LeapPad2 has hardware crypto that LeapPad1 did not:

    drivers/crypto/nxp3200/
        nx_aes.c, nx_aes_linux.c, nx_aes_regmap.h, nx_aes_ioctl.h
        sysapi.c/h, nx_writeio.h
    arch/arm/mach-nxp3200/prototype/module/nx_ecid.c/.h
        ECID = Electronic Chip ID — a per-chip unique identifier

A hardware AES engine plus a per-chip unique ID is the classic recipe for
device-bound content encryption. If cartridge or title content is AES
encrypted with a key derived from or wrapped by the ECID, then:
  * dumping a cart gives you ciphertext,
  * and the emulator needs the per-device key material to decrypt it.

THIS IS THE ONE THING THAT COULD BLOCK THE WHOLE PROJECT, so resolve it
early rather than at M8:
  [ ] Read nx_aes_ioctl.h — what does userspace ask the AES engine to do?
  [ ] Read nx_ecid.c — how is the chip ID read, and is it exposed to
      userspace (sysfs? ioctl?)
  [ ] On the device: dump the ECID (read-only) during the §8 capture.
  [ ] strace the title-launch path and watch for opens on the crypto device.
  [ ] Check whether Flash Lite .swf content is stored plaintext — if the
      SWFs are readable as-is, encryption may only cover native titles, or
      may not be used at all.
  >>> The fastest single test: `file` and `binwalk` a few files pulled off
      your own device's /LF tree. If SWFs are plain SWFs, breathe out.
      Your device already has readable modified SWFs on it (you swapped one
      for The Impossible Quiz), which is fairly strong evidence that at
      least the Flash content layer is NOT encrypted. Good sign.

7. THE SHIM ARCHITECTURE  (unchanged from rev 2 — restated here)
--------------------------------------------------------------------------------
No boot. No kernel. One process under qemu-arm, with faked devices.

    ┌─ qemu-arm (one process) ───────────────────┐
    │   Flash Lite / Brio / app     (ARM)        │
    │                │                           │
    │           libc: open/mmap/ioctl            │
    │                │                           │
    │     [ LD_PRELOAD shim.so — ARM ]           │
    │          │                  │              │
    └──────────┼──────────────────┼──────────────┘
          mmap │            ioctl │ state
               ▼                  ▼
        fb0.bin (framebuffer)  state.bin    ← ordinary host files
               ▲                  ▲
    ┌──────────┼──────────────────┼──────────────┐
    │   viewer (native x86-64, SDL2)             │
    │   composites layers → window @60Hz         │
    │   keyboard/mouse → evdev events ───────────┼──▶ back to guest
    └────────────────────────────────────────────┘

  DATA PATH (pixels): the guest mmap of a plain host file becomes a real
    host mmap. A native process mmaps the same file. Shared memory, zero
    copy, no protocol. Nobody intercepts pixel writes.
  CONTROL PATH (ioctls): LD_PRELOAD in the guest, because qemu-user rejects
    ioctls missing from its translation table with -ENOSYS. Catching them at
    libc level sidesteps the table AND lets us implement the semantics.
  VSYNC: fake it on a timer, or apps blocking on FBIO_WAITFORVSYNC stall.

  Cross-compile the shim with the drop's toolchain (uClibc 0.9.32, ARMv7
  EABI). Alternative worth remembering: a Raspberry Pi runs these binaries
  natively, no QEMU at all — same shim, one less variable.

8. FLASH LAYOUT, RECOVERY, AND GETTING A CLEAN ROM
--------------------------------------------------------------------------------
PARTITIONS (LeapPad2):
  Name         Offset       Size         Device      Media
  ---------------------------------------------------------
  Boot Loader  0x00000000   0x0007E000   /dev/mtd0   NOR
  MfgData0     0x0007E000   0x00001000   /dev/mtd1   NAND
  MfgData1     0x0007F000   0x00001000   /dev/mtd2   NAND
  Reserved     0x00080000   0x00400000   /dev/mtd3   NAND
  Kernel       0x00480000   0x01000000   /dev/mtd4   NAND   (16 MB)
  RFS          0x01480000   0x0A000000   /dev/mtd5   NAND   (160 MB)
  Bulk         0x0B480000   0xF4C00000   /dev/mtd6   NAND   (~3.9 GB)
  Cartridge    —            —            —           Cartridge NAND

UBI (RFS): vol_name=ubi_rfs, vol_size=164380672
           -m 4096 -e 1048576 -c 158 -s 4096 -O 4096
  (page 4096, LEB 1 MB, 158 LEBs, subpage 4096, VID offset 4096)
  NOTE these differ from LeapPad1's values — use these.
  A dd of RFS is a UBI container, not a mountable fs. Attach UBI on-device
  or extract offline with ubireader/ubidump.

FIRMWARE FILE TYPES: Surgeon = CBF, Kernel = uImage, RFS = UBI.

BOOT KEY COMBOS (from eLinux — these are your recovery lifeline):
  U-Boot monitor   serial required. Hold shift+M on the HOST keyboard,
                   power up the device, then *very quickly* type o then n.
  USB Boot/Surgeon hold D-pad RIGHT + HOME while powering up.
  Mfg Test         hold VOL-UP + VOL-DOWN while powering up, keep holding
                   until the test screen appears.

  >>> Mfg Test is worth running and photographing BEFORE you change
      anything. It's LeapFrog's own per-subsystem hardware test and it tells
      you what "correct" looks like for display, touch, audio and buttons.

GETTING A CLEAN ROM (your firmware is modified — Impossible Quiz, etc.):
  OpenLFConnect (jrspruitt) does NOT download from LeapFrog's servers — it
  only uploads local firmware files to the device. Confirmed from its docs.
  It supports LeapPad2 over USB Mass Storage (v2 firmware) and does
  "formats and copies everything you need". Archived June 2023, read-only,
  and the author stopped in 2014 citing breakage on newer distros — so
  expect to run it in an old Python 2 environment or a VM.

  So a stock image must come from:
    1. LFConnect's local cache on a PC that ran it
       (ProgramData\Leapfrog\LeapFrog Connect\, device-named subfolder)
    2. LeapFrog's update servers, IF still alive — test in the Win7 VM
    3. Community mirrors / archive.org
  .lfp = ZIP, .lf2 = bzip2. Renamed extensions, nothing more.

  >>> IMPORTANT: dump your CURRENT modified firmware anyway, before
      reflashing. It is the only copy, it proves what you already changed,
      and a known-modified image is genuinely useful for testing the
      emulator (you know exactly what should appear). Don't overwrite it.

    *** THE INJECTION PROBLEM AND HOW TADPOLE SOLVES IT ***
    LD_PRELOAD DOES NOT WORK. LeapFrog's uClibc 0.9.32 was built without
    __LDSO_PRELOAD_ENV_SUPPORT__ — the guest loader never opens an
    LD_PRELOAD path at all, confirmed with a known-good library so it is
    not a fault in our object. ("LD_PRELOAD" appears in ld-uClibc only in
    the list of variables it scrubs for setuid binaries.)

    Instead Tadpole IMPERSONATES A LIBRARY the target already links:
      * copy the real lib aside, patching its SONAME in place to a
        same-length name (libdl.so.0 -> libdl.so.9, libz.so.1 -> libz.so.9)
      * build the shim with SONAME set to the ORIGINAL name and DT_NEEDED
        on the renamed real one
      * put it first in LD_LIBRARY_PATH
    Our open/ioctl then win symbol lookup, everything else resolves straight
    through to the real library, and dlsym(RTLD_NEXT, ...) works normally.
    Two variants are needed because the targets link different things:
      libdl.so.0  -> AppManager (libdl is #22 in its DT_NEEDED, libc is #33)
      libz.so.1   -> imager-fb / drawtext-fb / flipbook-fb / fbtest
                     (these link no libdl at all)

    OTHER THINGS THAT HAD TO BE RIGHT:
      * smem_len must cover MULTIPLE screens. Brio allocates buffers inside
        one framebuffer and flips with FBIOPAN_DISPLAY — observed live as
        "AllocBuffer: new buf offset 000FF000, length 0007F800", i.e. two
        screens in. Tadpole advertises yres_virtual = yres * 8.
        The viewer honours yoffset when compositing.
      * /dev/input/event0..24 must EXIST as directory entries or the guest
        never enumerates past event1. Placeholder files in the sysroot fix
        it; the shim intercepts open() on them regardless.
        LeapFrog's own usr/bin/make_dev_nodes.sh independently confirms the
        required set: /dev/input/event0..4 and /dev/fb0..2 — exactly ours.
      * ubireader drops exec bits; chmod +x every ELF and script.
